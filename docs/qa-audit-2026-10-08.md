# Ridewallah — QA, security & reliability audit (2026-10-08)

**Verdict: Not Ready.** Three money/dispatch race conditions, an OTP bypass, a fare that the client controls,
simulated payments and simulated safety features block launch. Details, evidence and fixes below.

Everything marked *Executed* was run in this audit; *Code review* items were found by reading the code and were not run.

**Roles:** customer, rider (driver), admin (single shared login, no support/finance sub-roles, no audit log).
**Vehicles:** bike, auto, mini, sedan, SUV (AC/Non-AC for cars), parcels with weight slabs.
**Pricing (from catalog + code):** base + ₹/km + ₹/min, minimum fare, Non-AC −15 %, parcels 90 % + weight charge, surge × multiplier on weekdays 8–11 and 18–21 IST, coupons (percent with cap / flat).
**Ride states (rides-server.ts):** `Searching` (offered to one rider at a time, 20 s offer) → `Arriving` (accepted) → `Arrived` → `Started` (customer's 4-digit OTP) → `Completed`; `Cancelled` from any non-terminal state by customer, or from active states by the assigned rider; search auto-cancels after 75 s. Payment is separate (`rides.paid`). `Assigned` exists in the enum but is unused; there is no no-show, reassignment, refund, payment-failed or scheduled-ride state.
**Existing tests before this audit:** none. No CI.

## 2. Test environment & safety

- **No isolated test database exists.** Tests ran against the configured Supabase project (also used by the live site) using only synthetic accounts (`*@ridewallah.test`, plates `TEST QA…`), deleted after every run (verified: 0 test logins / test riders left).
- Test rides use one vehicle type (bike); `assertIsolated()` refuses to run if any real rider is online for it, so no real rider received a test offer.
- No real payments, SMS, email or emergency services exist to trigger. Load was bounded (≤ 20 parallel requests).
- Secrets were never printed; reports redact tokens.

**Recommendation:** create a separate Supabase project for tests/staging before further testing.

## 4. Bug report

Severity: **Critical** (money, safety or auth broken), **High**, **Medium**, **Low**.

**B1 — Critical — Duplicate rider earnings and commission on repeated completion** (rider, admin finance)
Repro: R6 — complete the same `Started` ride 5× in parallel. Expected 1 wallet entry + 1 commission; actual 4 + 4 (3/3 runs).
Root cause (established): `advanceForRider` updates with `.eq("status", r.status)` but never checks how many rows changed, then calls `settle()` unconditionally — every request that read `Started` before the first update writes earnings. `app/lib/rides-server.ts` `advanceForRider` / `settle`.
Fix: update with `.select("id")` and only settle when a row was returned; add a unique index on `wallet_txns(ride_id, kind)` (needs a ride_id column) and `transactions(ride_id, kind)` as a backstop. Regression: R6.

**B2 — Critical — One rider can be offered and accept several rides at once** (rider, customer)
Repro: R10 — 4 customers book in parallel while one rider is free → rider holds 4 offers, accepts all 4 → 4 active rides (3/3 runs).
Root cause (established): `offerNext` computes "busy/holding" then updates in separate statements (check-then-act); `acceptForRider` doesn't check the rider's existing active ride; no DB constraint.
Fix: partial unique indexes `rides(offered_to) where status='Searching' and offered_to is not null` and `rides(driver_id) where status in (active)`; do dispatch in a Postgres function with `FOR UPDATE SKIP LOCKED`; reject accept when the rider already has an active ride. Regression: R10.

**B3 — High — Parallel taps create multiple active bookings for one customer**
Repro: R9 — 5 parallel `book` calls → 5 (then 4, 4) active rides; sequential double booking is correctly refused.
Root cause (established): count-then-insert in `book()`. Fix: partial unique index `rides(customer_id) where status in ('Searching', active)`; map the violation to "You already have a ride in progress". Regression: R9.

**B4 — Critical — Assigned rider can read the ride OTP from the database** (customer safety, fraud)
Repro: S1 — as the assigned rider, `select otp from rides where id = …` via Supabase REST → OTP returned. The rider can start the trip without meeting the customer and complete it for earnings.
Root cause (established): RLS policy `own rides` grants the driver every column. Fix: `revoke select (otp) on rides from authenticated` (grant other columns explicitly) and give the customer their OTP only via the server action (already done in `currentForCustomer`); change client `select("*")` on rides to explicit columns. Regression: S1.

**B5 — High — Rider sets their own waiting fee** (customer overcharge)
Repro: R5 — start the trip immediately after arriving with `waitFee: 500` → ₹500 stored. Root cause: `advanceForRider` trusts the client value (capped at ₹500). Fix: store `arrived_at` and compute the fee on the server from the free window and per-minute rate. Regression: R5.

**B6 — Critical (launch) — Distance and fare come from client-chosen ids, not real locations**
Repro: Q2 — any pickup/drop names with the same ids price identically (5.5 km); names are free text. Root cause: no maps/geocoding; `tripEstimate` hashes two ids. Fix: real geocoding + routing server-side; price from coordinates; validate service area. Regression: Q2.

**B7 — High — Admin login has no rate limiting, lockout, MFA or roles**
Repro: H5 — 25 wrong passwords via direct POST all processed. File: `app/admin/actions.ts` `login`. Fix: rate-limit by IP + account, lockout with backoff, move admins to Supabase Auth with roles (admin/support/finance) and MFA, add an audit log. Regression: H5.

**B8 — High — Self-dispatch: a login with both roles is offered its own booking**
Repro: R20. Fix: exclude riders whose `user_id` equals the booking customer's `user_id` in `offerNext`. Regression: R20.

**B9 — Critical (launch) — Payments are simulated**
Any non-cash ride becomes "paid" when the customer taps Pay (`payForCustomer`); wallet has no balance (Q8); card "Visa ending 4821" and wallet "₹240" are hardcoded in `BookingScreens.tsx`. No gateway, webhooks, failures, refunds or reconciliation exist. Fix: integrate a gateway (e.g. Razorpay test mode) with signed, idempotent webhooks; real wallet ledger. Regression: Q8 + new webhook tests.

**B10 — Medium — Coupon rules not enforced**
Q3: AUTO20 applies to non-Auto rides; Q4: FIRST50 reusable; Q5: expired coupons apply; `uses` never incremented, no per-user limits, "rides above ₹80"/"Sat & Sun" not enforced. Fix: model vehicle, min fare, days, first-ride, per-user and total limits as columns and enforce in `price()`; record redemptions atomically. Regression: Q3–Q5.

**B11 — Medium — No limit on ride-OTP guesses**
R4: 12 wrong guesses then the correct OTP works. 4-digit space (10 000). Fix: lock the ride's OTP after ~5 failures and notify the customer. Regression: R4.

**B12 — Medium — Active ride stuck when the rider is suspended mid-trip**
R19: rider can't complete (correct), but nothing resolves the ride and the customer can't book again. Fix: admin "resolve/cancel ride" action; timeout for stale active rides; let the customer end/cancel with a reason. Regression: R19.

**B13 — Medium — Rider can read passenger email, user id, block and complaint fields**
S10. Fix: column-level grants or a restricted view exposing only name, phone (ideally masked), rating. Regression: S10.

**B14 — Medium — Intermittent "Couldn't load catalog from Supabase: undefined" fails bookings**
Seen 3 times in 3 suite runs under parallel load (R13/R14 run 1, L3 run 3); not reproduced in 120 isolated parallel reads. Hypothesis: transient upstream errors under bursts — each booking runs 7 catalog queries. The message is `undefined` because the error object has no message. Fix: cache the catalog server-side (e.g. 30–60 s), retry transient failures, log the full error. Regression: L3.

**B15 — High — Vulnerable dependencies**
`next@16.2.6` (critical: Server Actions DoS, proxy bypass; GHSA-6gpp-xcg3-4w24), `postcss`, `sharp`, `source-map-js` (high). Fix: upgrade to `next@16.4.0`+ and re-run `npm audit`.

**B16 — Low — Weak server-side account rules**
API signup accepts 6-char passwords (UI requires 8); email unconfirmed and phone unverified — anyone can register someone else's email/phone. Fix: set Supabase minimum password length; enable email confirmation with custom SMTP; verify phone by OTP for riders.

**B17 — Low — Leftover diagnostic/legacy functions**
`debug_rls()` (service-role only), `claim_profiles()`, `my_phone()` remain. Fix: `drop function public.debug_rls();` and remove unused ones.

**B18 — Medium (requirements conflict) — No reassignment after a rider cancels**
The ride is cancelled and the customer must rebook (R17). Decide the rule; if reassignment is wanted, return the ride to `Searching` with the rider in `declined_by`.

**B19 — Low — Pickup equal to destination is accepted** (P10). Reject identical places.

### Code-review findings (not executed)

- Offline riders can still accept an offer they already hold (`acceptForRider` doesn't check `online`).
- Rider preferences (cash rides, parcels, "AC working") are not used by dispatch.
- Account deletion is not implemented (customer "Delete account" only shows a message); no forgot-password.
- SOS, share-trip and support chat are simulated; no incident records; no tickets created from apps.
- Rider documents and bank details are not uploaded or stored.
- Admin dashboard "Today's revenue/rides" and weekly chart are hardcoded; rider earnings summary (₹1,240, 3 trips) and wallet (₹1,840) are sample numbers.
- Client shows surge from the device clock while the server uses IST — displayed and charged fares can differ near peak boundaries.
